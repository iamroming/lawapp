1. CRITICAL - SECURITY FLAWS (Fix Immediately)
================================================================================

[#1] HARDCODED SUPER ADMIN CREDENTIALS IN SOURCE CODE
  Location : src/lib/super-admin.ts
  Issue    : Real email (mubb@ymail.com) and password (123mubeen) are hardcoded
             in plain text and committed to git.
  Impact   : Anyone with repo access has owner-level platform access.
  Fix      : Move to environment variables + server-side validation only.

[#2] CLIENT-SIDE AUTH BYPASS FOR SUPER ADMIN
  Location : src/app/(auth)/login/page.tsx (lines 24-66)
  Issue    : Super admin check runs in browser JavaScript BEFORE Supabase
             authentication. The isSuperAdmin() function compares credentials
             in plain JS that anyone can read via View Source.
  Impact   : Credentials are visible to anyone inspecting the page.
  Fix      : Move all auth logic to server-side API routes or middleware.

[#3] SUPER ADMIN UPSERT FROM CLIENT SIDE
  Location : src/app/(auth)/login/page.tsx (lines 55-58)
  Issue    : After login, the client directly upserts into the super_admins
             table with access_level: "owner".
  Impact   : Any authenticated user could call this Supabase query directly
             and elevate themselves to owner.
  Fix      : Only server-side code should write to super_admins table.

[#4] RLS POLICIES GRANT FULL ACCESS TO ALL DATA
  Location : supabase/schema.sql (lines 229-265)
  Issue    : All tables (clients, cases, hearings, documents, time_entries,
             invoices, payments, notes) use auth.role() = 'authenticated'
             policies. This means ANY logged-in user can read, modify, or
             delete ANY other user's data.
  Impact   : Lawyer A at Firm X can see and modify ALL of Lawyer B's data
             at Firm Y. Complete data leak across tenants.
  Fix      : Add user_id = auth.uid() or firm_id conditions on every table.

[#5] NO TENANT ISOLATION
  Location : All RLS policies
  Issue    : There is no concept of firm_id or user_id ownership on data.
             Cases, clients, documents have created_by but RLS doesn't
             enforce ownership.
  Impact   : Law firms will NEVER use this - their client data (which is
             legally confidential) leaks to every other user on the platform.
  Fix      : Add firm_id to all tables, enforce in RLS.

[#6] CONFIDENTIAL DOCUMENTS HAVE PUBLIC URLs
  Location : src/app/(dashboard)/documents/page.tsx (line 97)
  Issue    : getPublicUrl() is used for ALL uploaded documents, including
             those marked as is_confidential = true.
  Impact   : Anyone with the URL (guessable, shareable) can download
             confidential legal documents.
  Fix      : Use signed URLs with expiration for all document access.

[#7] ADMIN/SUPER-ADMIN CHECKS ARE CLIENT-SIDE ONLY
  Location : src/app/(admin)/layout.tsx, src/app/(super-admin)/layout.tsx
  Issue    : Role checks happen in useEffect after component mount. Content
             flashes before redirect. Routes are technically accessible.
  Impact   : A determined user can bypass the redirect and access admin pages.
  Fix      : Add role checks in middleware or server-side layout data fetching.

[#8] NO RATE LIMITING ON AUTH ENDPOINTS
  Location : Login and signup pages
  Issue    : No rate limiting on login attempts, signup, or password reset.
  Impact   : Vulnerable to brute force attacks, credential stuffing, and
             automated account creation.
  Fix      : Add rate limiting via Supabase Edge Functions or middleware.

[#9] NO CSRF PROTECTION BEYOND DEFAULTS
  Location : Throughout the application
  Issue    : No explicit CSRF token implementation.
  Impact   : Cross-site request forgery attacks possible.
  Fix      : Implement CSRF tokens for state-changing operations.

[#10] WEAK PASSWORD FOR OWNER ACCOUNT
  Location : src/lib/super-admin.ts
  Issue    : Password "123mubeen" is extremely weak and easily guessable.
  Impact   : Account takeover trivial.
  Fix      : Enforce strong password requirements (12+ chars, mixed case,
             numbers, symbols).

2. HIGH - ARCHITECTURE FLAWS
================================================================================

[#11] ZERO API ROUTES
  Issue    : No src/app/api/ directory exists. All mutations go directly
             from client to Supabase database.
  Impact   : No server-side validation, no business logic layer, no audit
             trail, no centralized error handling.
  Fix      : Create API routes for all mutations.

[#12] ZERO SERVER COMPONENTS
  Issue    : Every page uses "use client". Zero server components exist.
  Impact   : Defeats Next.js App Router benefits. No SSR, no SEO on any
             page, slower initial loads, no server-side data fetching.
  Fix      : Convert data-fetching pages to Server Components where possible.

[#13] NO ERROR BOUNDARIES
  Issue    : No React error boundary components exist anywhere.
  Impact   : One component crash kills the entire page with a blank screen.
  Fix      : Add error.tsx to all route segments, add global error boundary.

[#14] NO TESTS AT ALL
  Issue    : Zero test files. No Jest, no Vitest, no Playwright, no Cypress.
             No testing framework even configured.
  Impact   : Can't verify anything works. Every change risks regressions.
             Cannot demonstrate quality to potential buyers.
  Fix      : Add unit tests for critical paths, E2E tests for main flows.

[#15] NO PAGINATION
  Issue    : All list views load ALL records at once. Activity logs use
             .limit(200) or .limit(500) with no pagination UI.
  Impact   : Performance degrades as data grows. After a few months of use,
             pages will be very slow.
  Fix      : Add cursor-based or offset pagination on all list views.

[#16] ACTIVITY LOGGING EXISTS BUT IS NEVER USED
  Issue    : The log_activity() database function exists in admin-schema.sql
             but is NEVER called from any application code.
  Impact   : Activity logs table will always be empty. Admin cannot track
             what users are doing.
  Fix      : Call log_activity() on every mutation (create, update, delete).

[#17] SUBSCRIPTION LIMITS ARE NEVER ENFORCED
  Issue    : Subscription plans define max_cases, max_users, max_storage_mb
             but no code checks these limits before allowing operations.
  Impact   : Free plan users can create unlimited cases, users, and storage.
             No revenue from subscription model.
  Fix      : Add limit checks before every create operation.

[#18] NO ENVIRONMENT VARIABLE VALIDATION
  Issue    : .env.local has placeholder values. Non-null assertions (!) on
             process.env.NEXT_PUBLIC_SUPABASE_URL will crash at runtime.
  Impact   : App crashes silently if environment variables are missing.
  Fix      : Add validation at startup using @t3-oss/env-nextjs or similar.

[#19] MISSING EDIT PAGES
  Issue    : /cases/[id]/edit and /clients/[id]/edit are linked in the UI
             but the page files do not exist.
  Impact   : Users click "Edit" and get 404 errors.
  Fix      : Create the edit pages.
