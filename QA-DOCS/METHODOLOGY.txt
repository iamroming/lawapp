CASEFILES - BUG FINDING & FIXING METHODOLOGY
=============================================
How 56 bugs were found and fixed across a 208-page Next.js app

================================================================================
PART 1: HOW BUGS WERE FOUND
================================================================================

STEP 1: STATIC ANALYSIS (Code Reading)
---------------------------------------
Read every file in the codebase systematically:
- All 60+ API routes in src/app/api/
- All 208 page components in src/app/
- All library files in src/lib/
- All components in src/components/

For each file, trace the data flow:
  Form → fetch() → API route → Supabase query → response → UI render

Look for mismatched expectations:
- API returns flat array [..] but page expects { data: [...] }
- Page sends field X but API expects field Y
- Query returns null but code accesses .data.property

Example: Quotation dropdowns empty
  Page: d.clients || []  (expects object)
  API:  return NextResponse.json(data)  (returns array)
  Fix:  Array.isArray(d) ? d : d.clients || []


STEP 2: PATTERN MATCHING (Find Similar Bugs)
---------------------------------------------
When one bug is found, search for the same pattern everywhere.

Example: expenses/new page uses direct Supabase insert without firm_id
  → Search: "supabase.from(" across all pages
  → Found: 28 pages with the same pattern
  → Fixed: All 28 pages

The pattern: bugs cluster. One wrong approach appears in multiple places.
Finding the pattern fixes many bugs at once.


STEP 3: ADVERSARIAL THINKING (Attack the App)
----------------------------------------------
Ask "what if?" questions that a malicious user would ask:

Security:
- "What if I'm from Firm A — can I download Firm B's documents?"
  → Found: documents/[id]/download had no firm_id filter
- "What if I guess a quotation UUID?"
  → Found: quotations/[id] had no firm_id filter
- "What if I extract the service-role key from DevTools?"
  → Found: super-admin pages embedded it in client bundle

Null Safety:
- "What if this RPC call fails?"
  → Found: case number would be null
- "What if items is null, not empty?"
  → Found: quotation creation crashes
- "What if billingCycle is not provided?"
  → Found: subscription change crashes

Edge Cases:
- "What if the user has no firm_id (solo user)?"
  → Found: tasks PATCH/DELETE always fail for solo users
- "What if empIds is empty?"
  → Found: performance page crashes with PostgREST error
- "What if RAZORPAY_KEY_ID is not set?"
  → Found: isRazorpayConfigured() crashes


STEP 4: ROLE-BASED TESTING (Trace as Each User)
-------------------------------------------------
Trace the same feature through each role:

Owner → Employee → Super Admin

Found:
- Admin pages used service-role client for getUser() → pages never load
- Employee forms missing firm_id → 403 Forbidden errors
- Super admin server actions had no auth check → any user could call them

Each role sees different data, has different permissions.
Bugs hide in the gaps between roles.


STEP 5: CRON/BACKGROUND JOB TESTING
------------------------------------
Ask "what happens when this runs without a user?"

- Deadline check cron: userId is null → .eq("created_by", null) matches nothing
- Cause list sync: same issue
- Daily digest: queries hearings.firm_id but hearings POST never set it

Background jobs run with service-role, not as a user.
Code written for user context breaks in cron context.


STEP 6: BUILD VERIFICATION
---------------------------
Run `npm run build` after every fix batch.

Catches:
- TypeScript errors (wrong types, missing imports)
- Missing dependencies
- Circular imports
- Dead code references


================================================================================
PART 2: HOW BUGS WERE FIXED
================================================================================

PRINCIPLE 1: FIX THE PATTERN, NOT JUST THE INSTANCE
----------------------------------------------------
Wrong approach: Fix expenses/new, then later find cases/new has same bug.
Right approach: Find the pattern (direct Supabase insert without firm_id),
then fix ALL 28 pages at once.

Example:
  Found: expenses/new doesn't include firm_id
  Searched: all pages using supabase.from().insert()
  Found: 28 pages with same issue
  Fixed: All 28 in one batch


PRINCIPLE 2: MINIMAL CHANGES
-----------------------------
Don't rewrite working code. Make the smallest change that fixes the bug.

Wrong: Rewrite entire API route
Right: Add one line: .eq("firm_id", profile.firm_id)

Wrong: Refactor entire auth system
Right: Add one line: if (!user) return 401


PRINCIPLE 3: FIX SECURITY FIRST
--------------------------------
Priority order:
1. Data leaks (cross-tenant access) → fix immediately
2. Auth bypass (no permission checks) → fix immediately
3. Broken features (crashes, wrong data) → fix next
4. Performance (N+1 queries, memory) → fix last

Example:
  C3 (document leak) → fixed before H1 (solo user task bug)
  Because data leak affects ALL users, solo user bug affects few.


PRINCIPLE 4: DON'T BREAK WORKING FEATURES
------------------------------------------
After each fix batch, run build to verify nothing broke.

If a fix might break something:
1. Read the surrounding code first
2. Understand what depends on this code
3. Make the minimal change
4. Build and verify

Example: Adding firm_id to hearing insert
  - Check: does the hearings table have a firm_id column?
  - Check: do other queries filter by firm_id on hearings?
  - Check: does the daily digest depend on hearings.firm_id?
  - Then add the field to the insert


PRINCIPLE 5: USE EXISTING PATTERNS
-----------------------------------
Don't invent new approaches. Copy what already works.

If one page correctly fetches profile and sets firm_id:
  const { data: profile } = await supabase
    .from("profiles").select("firm_id").eq("id", user.id).single();
  insert({ ..., firm_id: profile?.firm_id })

Copy this exact pattern to all other pages that need it.


PRINCIPLE 6: HANDLE BOTH FORMATS
---------------------------------
When API response format is uncertain:

  Array.isArray(d) ? d : d.cases || []

This handles:
- Direct array response: [..]
- Wrapped response: { cases: [...] }
- Empty/null response: []

More resilient than assuming one format.


PRINCIPLE 7: TWO-CLIENT PATTERN
--------------------------------
For pages that need both auth and admin access:

  // Browser client for auth (has user session)
  const authClient = createClient();
  const { data: { user } } = await authClient.auth.getUser();

  // Service-role client for data (bypasses RLS)
  const dataClient = createServiceRoleClient();
  const { data } = await dataClient.from("table").select("*");

Never use service-role for auth.getUser() — it has no session.

PART 3: BUG CLASSIFICATION SYSTEM
================================================================================

CRITICAL — Fix immediately, blocks production
  - Security: data leaks, auth bypass
  - Core feature broken: can't create cases, can't login
  - Data corruption: wrong amounts, missing fields

HIGH — Fix before production
  - Feature crashes: 500 errors, white screens
  - Wrong behavior: redirects to wrong page, shows wrong data
  - Edge cases that affect many users

MEDIUM — Fix in next sprint
  - Logic errors: wrong calculations, missing filters
  - Performance: N+1 queries, memory issues
  - Minor security: missing validation, error leaks

LOW — Fix when convenient
  - Cosmetic: wrong colors, dead code
  - Minor UX: missing loading states
  - Code quality: duplicate exports, unused imports

================================================================================
PART 5: LESSONS LEARNED
================================================================================

1. Multi-tenant apps need firm_id EVERYWHERE
   Every insert, every update, every query. Missing one = data leak.

2. Client-side Supabase is risky for writes
   RLS must be perfect. One missing policy = 403 error.
   Better: use API routes for all mutations.

3. Cron jobs are different from user requests
   No user context, no session, no RLS. Test with null userId.

4. Null is not empty
   .eq("field", null) doesn't match NULL in SQL.
   .is("field", null) does. Different behavior, easy to mix up.

5. Build errors hide runtime errors
   ignoreBuildErrors: true masks TypeScript issues.
   Fix TS errors to catch bugs at compile time.

6. One bug pattern = many bugs
   If one page has a bug, search for the same pattern.
   The same mistake is usually repeated across the codebase.

7. Security bugs cluster around data access
   Cross-tenant leaks happen where firm_id filtering is missing.
   Always add firm_id as the first filter in every query.

8. Test as each role
   Owner sees everything. Employee sees only their data.
   Super admin bypasses everything. Bugs hide in the gaps.
