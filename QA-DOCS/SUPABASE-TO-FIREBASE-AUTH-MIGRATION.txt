1. OVERVIEW & WHY FIREBASE AUTH
================================================================================

CURRENT STATE:
- Supabase Auth handles: email/password, Google OAuth, email verification,
  password reset, session management via cookies
- Supabase Postgres handles ALL database tables (profiles, cases, clients, etc.)
- Supabase RLS (Row Level Security) enforces data access rules

WHY MIGRATE AUTH ONLY:
- Firebase Auth has better Google OAuth integration (native support)
- Firebase Auth has built-in phone auth (useful for Indian market)
- Firebase Auth has better token management (ID tokens vs Supabase JWT)
- Firebase Auth is more widely documented and has larger community
- Firebase Auth supports more OAuth providers out of the box

WHAT STAYS ON SUPABASE:
- ALL database tables (profiles, cases, clients, invoices, etc.)
- Supabase Postgres as the database
- Supabase RLS policies (modified to use Firebase UID instead of Supabase UID)
- Supabase Storage (if used for documents)
- All API routes that query/write data

CRITICAL INSIGHT:
- The user ID (UUID) stored in profiles.id, cases.created_by, etc. will change
  from Supabase Auth UUIDs to Firebase Auth UIDs
- You MUST migrate existing user IDs in the database OR use a mapping table
- Option A: Migrate all existing user IDs (cleaner, one-time migration)
- Option B: Add a firebase_uid column and map (less disruptive)

RECOMMENDATION: Option A — Migrate all user IDs at once during a maintenance
window. It's cleaner and avoids perpetual mapping overhead.

4. FIREBASE PROJECT SETUP
================================================================================

Step 1: Create Firebase Project
  - Go to https://console.firebase.google.com
  - Create new project (e.g., "casefiles-prod")
  - Enable Google Analytics (optional)

Step 2: Enable Authentication
  - Go to Authentication → Sign-in method
  - Enable Email/Password
  - Enable Google (add support email)
  - Enable Phone (optional, for Indian market)

Step 3: Register Web App
  - Go to Project Settings → General → Your apps
  - Add Web app (e.g., "casefiles-web")
  - Copy firebaseConfig object

Step 4: Get Service Account Key
  - Go to Project Settings → Service accounts
  - Generate new private key (JSON)
  - Save as firebase-service-account.json (DO NOT commit to git)

Step 5: Set up OAuth Redirect URIs
  - In Firebase Auth → Settings → Authorized domains
  - Add your production domain (e.g., casefiles.in)
  - Add localhost for development

Step 6: Configure Google OAuth Consent Screen
  - In Google Cloud Console → APIs & Services → OAuth consent screen
  - Add Firebase Auth redirect URI to authorized redirects

8. GOOGLE OAUTH MIGRATION
================================================================================

CURRENT (Supabase):
  Login page → supabase.auth.signInWithOAuth({ provider: "google" })
    → Redirects to Supabase → Google → /auth/callback?code=...
    → supabase.auth.exchangeCodeForSession(code)
    → Session cookies set

NEW (Firebase):
  Login page → firebase signInWithPopup(googleProvider)
    → Popup closes, Firebase sets auth state
    → OR: signInWithRedirect for mobile

  Callback is handled CLIENT-SIDE by Firebase automatically.
  No server-side /auth/callback route needed for Google.

  BUT: We need to create a session cookie for server-side auth:
    1. Client gets Firebase ID token: await user.getIdToken()
    2. POST to /api/auth/session with the ID token
    3. Server verifies token with Firebase Admin SDK
    4. Server creates HTTP-only session cookie
    5. Subsequent requests use session cookie for auth

ENV SETUP:
  - In Firebase Console → Authentication → Sign-in method → Google
  - Enable and add support email
  - Copy Web Client ID and Web Client Secret to Firebase project settings
  - These are SEPARATE from Supabase's Google OAuth credentials
  - You may need to update Google Cloud Console OAuth consent screen

================================================================================

SIGNUP:
  BEFORE: POST /api/auth/signup → supabaseAdmin.auth.admin.createUser()
  AFTER:  POST /api/auth/signup → firebaseAdmin.auth().createUser()
          {
            email, password, displayName,
            emailVerified: false
          }

LOGIN:
  BEFORE: supabase.auth.signInWithPassword({ email, password })
  AFTER:  Firebase signInWithEmailAndPassword(auth, email, password)
          Then: POST /api/auth/session with ID token to create session cookie

PASSWORD RESET:
  BEFORE: supabase.auth.resetPasswordForEmail(email, { redirectTo })
  AFTER:  Firebase sendPasswordResetEmail(auth, email)
          Firebase handles the email link automatically
          No custom redirect needed (or use actionCodeSettings for custom URL)

EMAIL VERIFICATION:
  BEFORE: supabase.auth.resend({ type: "signup", email })
  AFTER:  Firebase sendEmailVerification(user)
          OR: Set emailVerified: true during signup (skip verification)

10. SESSION & MIDDLEWARE MIGRATION
================================================================================

CURRENT (Supabase):
  - Supabase uses JWT access token in cookies
  - middleware.ts calls supabase.auth.getUser() which verifies JWT
  - Session refresh happens automatically via cookie setAll

NEW (Firebase):
  - Firebase uses ID tokens (short-lived, 1 hour)
  - For SSR, create a SESSION COOKIE (longer-lived, HTTP-only)
  - Middleware verifies session cookie on every request

MIDDLEWARE FLOW:
  1. Request comes in
  2. Read session cookie (firebase-session)
  3. Verify with Firebase Admin SDK: adminAuth.verifySessionCookie(cookie)
  4. If valid: attach user info to request headers
  5. If invalid: redirect to /login (for protected routes)
  6. Refresh cookie if needed (token refresh)

HELPER FUNCTION:
  export async function verifyFirebaseToken(request: NextRequest) {
    const sessionCookie = request.cookies.get('firebase-session')?.value;
    if (!sessionCookie) return null;
    try {
      const decoded = await adminAuth.verifySessionCookie(sessionCookie);
      return { id: decoded.uid, email: decoded.email, ... };
    } catch {
      return null;
    }
  }

12. DATABASE (SUPABASE POSTGRES) — WHAT STAYS
================================================================================

CRITICAL: Supabase is STILL your database. Only AUTH moves to Firebase.

All these stay unchanged:
  - profiles table (but id column changes from Supabase UUID to Firebase UID)
  - cases, clients, invoices, payments, documents tables
  - All other tables
  - All RLS policies (updated to check Firebase UID)
  - All database queries in src/lib/supabase/queries.ts
  - All API route data operations

DATABASE CHANGES REQUIRED:
  a) profiles.id: Change from Supabase auth UUID → Firebase UID (string)
     - Firebase UIDs are strings like "abc123Def456..."
     - Supabase UIDs are UUIDs like "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11"
     - If you migrate, all foreign keys referencing profiles.id must update

  b) RLS policies: Update auth.uid() calls
     - Supabase: auth.uid() returns Supabase auth user UUID
     - Firebase: Need to pass Firebase UID via request header or JWT claim
     - Option: Use a Supabase function to get Firebase UID from header

  c) MIGRATION STRATEGY:
     - Create a migration table: user_id_map (supabase_uuid → firebase_uid)
     - Run migration: For each Supabase auth user, create Firebase user
     - Update all foreign keys in batch
     - OR: Add firebase_uid column to profiles and use that going forward

ROLLBACK TIME: < 1 hour (revert code changes, redeploy)

PREVENTION:

  - Keep dual auth running for 1-2 weeks
  - Monitor error rates during migration
  - Have database backup before user ID migration

  - Phase 7 (Database): 4-6 hours (including testing)
  - Phase 8 (Cleanup): 1-2 hours
  TOTAL: ~25-36 hours

RISKS:
  - User ID migration is the riskiest part (foreign key updates)
  - RLS policy changes need careful testing
  - Session cookie handling is complex (CSRF, security)
  - Google OAuth redirect URIs need to be updated
  - Email templates (verification, reset) need to be customized in Firebase

RECOMMENDATION:
  - Start with Phase 1-2 (setup + parallel) — no risk
  - Test Firebase auth thoroughly before cutting over
  - Consider keeping Supabase auth as fallback for 2 weeks
  - Do database migration during a maintenance window (low traffic)
